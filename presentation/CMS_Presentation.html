Project Overview

What is CMS?

A relational database application for law enforcement operations. It lets officers register incidents, manage cases, track evidence, issue warrants, and monitor court proceedings — all with a complete audit trail baked in.

Incident and Case Management

FIR-style registration, case file creation, and investigator assignment in one place.

Person Registry

Suspects, victims, and witnesses all in a unified table with role tracking per case.

Evidence and Custody

Full chain of custody logs with every transfer timestamped for accountability.

Court and Warrants

Warrant tracking, arrest records, hearing schedules, and charge sheet management.

AI Risk Scoring

Risk scores and recidivism likelihood stored directly as database columns for easy querying.

Audit Trail

Every write operation is logged with both the old and new values captured.

Mapping Algorithm

ER to Relational Mapping: Steps 1 to 3

Step 01 · Regular Entity Types

20 Entities Mapped

Each regular entity gets its own relation with simple attributes. Composite attributes are decomposed, so the location on crime_incidents becomes separate latitude and longitude columns.

Step 02 · Weak Entity Types

3 Weak Entities Handled

login_sessions owned by users, evidence_custody_log owned by evidence, and court_hearings owned by court_cases. Surrogate primary keys are used and the owner foreign key carries ON DELETE CASCADE.

Step 03 · Binary 1:1 Relationships

4 One to One Relationships

Enforced using a foreign key plus a UNIQUE constraint: case_files to crime_incidents, court_cases to case_files, charge_sheets to case_files, and medical_records to persons.

Mapping Algorithm

ER to Relational Mapping: Steps 4 to 7

Step 04 · 1:N Relationships

FK on the N-Side

All one to many relationships are handled by placing a foreign key on the many side. Two unary self-references exist: crime_types has a parent_id and users has a created_by field.

Step 05 · M:N Relationships

6 Junction Tables Created

All many to many relationships are resolved through junction tables: case_persons, case_officers, case_witnesses, case_victims, case_suspects, and person_associates.

Step 06 · Multi-valued Attributes

2 Intentional Exceptions

Two multi-valued attributes are kept as comma-separated strings for simplicity: persons.aliases and modus_operandi.tags. Both are flagged and documented in the schema notes.

Step 07 · N-ary Relationships

No Ternary Relationships

All relationships in CMS are binary. The AI scoring module uses a polymorphic pattern with subject_type and subject_id columns for the flexibility needed without adding ternary complexity.

Database Design

Normalization and Constraints

1NF

All Attributes Atomic

Aliases and tags are intentional exceptions kept as comma-separated strings for simplicity, and both are clearly noted as such in the documentation.

2NF

No Partial Dependencies

All non-key attributes depend on the full primary key. Surrogate integer primary keys eliminate any composite-key partial dependency issues entirely.

3NF

No Transitive Dependencies

Every non-key attribute depends only on the primary key, not on any other non-key attribute. This holds across the full schema.

BCNF

Every Determinant is a Superkey

All functional dependencies satisfy BCNF. Every core table in the schema has been verified to meet this requirement.

PRIMARY KEY on every table FOREIGN KEY with ON DELETE CASCADE UNIQUE on badge_number, username, email UNIQUE on incident_id in case_files CHECK constraints on status enums Triggers for audit log population has_active_warrant trigger-maintained Indexes on all FK and queried columns
Schema Design

Schema Highlights

Geographic Hierarchy

Countries to Provinces to Districts to Cities to Areas. A full 5-level location system where a foreign key chain ensures referential integrity at every single level.

Modus Operandi Table

Captures exactly how repeat offenders operate: method used, tools, target type, and typical time window. Linked to both person and crime type to support behavioral profiling.

AI Analysis Results

A polymorphic table with analysis_type, subject_type, subject_id, result_json, confidence, and model_version. Stores risk scores and recidivism predictions without any model training in scope.

Incident Amendments

A dependent audit entity tied to crime_incidents. Records who amended the incident, what changed, and exactly when. This supports truly immutable investigation records over time.

Security

Security Architecture and Audit Trail

Role-Based Access

Officers, detectives, supervisors, prosecutors, and admins each have distinct scopes. The role column in the users table controls what each person can see and do.

Login Security

Failed login attempts are tracked, accounts can be locked via the locked_until column, and new accounts carry a must_change_password flag to force a reset on first login.

Session Tracking

The login_sessions table records every login and logout event along with the IP address and workstation ID, giving a full session trail for every user.

Warrant Control

The has_active_warrant flag is maintained automatically by a trigger. Warrants expire on their own through the expires_at column, so nothing needs to be manually cleaned up.

Issue Report

Critical Issues and Remediation

Critical

Schema Desynchronization

The schema.sql file is outdated and is missing the medical_records table as well as columns like is_identified, photo, and personStatus inside the persons table.

Fix: Regenerate schema.sql from JPA entities and add a schema validation script to the CI/CD pipeline going forward.

High

Hardcoded Credentials

Database passwords are sitting in db.properties and admin passwords are exposed directly in SampleDataService.java inside the source code repository.

Fix: Move all secrets to environment variables, exclude .env from version control, and force a password change on every user's first login.

High

Brittle Data Seeding

SampleDataService.java relies on manual ALTER TABLE and UPDATE statements, including a hardcoded DETECTIVE to SUPERVISOR role update that could break at any point.

Fix: Switch to Flyway or Liquibase versioned migrations and replace the manual SQL with proper V1__ and V2__ migration files.

Medium

Deprecated Hibernate APIs

The build is throwing deprecation warnings right now. This means the code could break when the project is updated to a newer version of Hibernate down the line.

Fix: Refactor all deprecated calls, add unit tests for the data seeding logic, and verify compatibility with the current Hibernate version.

Course Outcome Mapping

CLO-2 · Complex Schema Design

31 Tables with Specialization Hierarchies

The schema includes crime type parent-child structures, person roles that vary per case, evidence type classification, multiple many to many relationships requiring junction tables, and one to one cardinality enforced through UNIQUE constraints.

CLO-3 · Concurrency and Transactions

Real Conflict Scenarios

Two officers updating the same case at the same time is a write-write conflict. A custody transfer must write to both evidence and custody_log atomically. A warrant status change must never leave the system in a partial state. These were all studied through isolation levels.

CLO-4 · SQL DDL and ERD Implementation

Full DDL with Normalization

Complete SQL DDL written with primary keys, foreign keys, constraints, and triggers for audit logging. Schema normalized to 3NF and BCNF. The ERD was designed in a formal tool and mapped step by step using the full ER to Relational algorithm.

Interdisciplinary · AI Integration

AI Risk Scores in the Database

Risk scores and recidivism predictions are stored as database columns in risk_score and the ai_analysis_results table. Model training is entirely out of scope. The database design covers storage, versioning, and audit linkage of AI-computed values only.
