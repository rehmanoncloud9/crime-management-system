ER-to-Relational Mapping

Rule 1 — Strong Entities

Direct Table Mapping

Each strong entity becomes a relation. Single-attribute PKs use BIGINT UNSIGNED AUTO_INCREMENT. Multi-attribute natural keys expressed as composite UNIQUE constraints.

Rule 2 — Weak Entities

Inherited PKs + CASCADE DELETE

evidence is partial-key dependent on case_files. FK declared ON DELETE CASCADE so orphan evidence is impossible.

Rule 3 — ISA Hierarchy

Table-per-Subtype Strategy

persons is the supertype. users and civilians share its PK via a 1:1 FK, keeping subtypes independent without duplication.

Rule 4 — Binary M:N

Junction / Bridge Tables

The Case–Officer M:N relationship becomes case_officers(case_id, officer_id, role, assigned_at). The junction carries descriptive attributes — not just keys.

Rule 5 — Multivalued Attributes

Separate Lookup Tables

A person's multiple phone numbers → person_contacts(person_id, type, value). Avoids repeating groups, restoring 1NF.

Rule 6 — Referential Actions

Semantically Correct Cascades

Parent deletes → RESTRICT for court-critical records. CASCADE only where child records are meaningless without parent. SET NULL for soft references.

Normalization · Step 1

First Normal Form — Atomicity

⚠ Violation

Unnormalized

Incident(ID, Title, SuspectsList)
— SuspectsList = "Ali, Ahmed, Sara"

Repeating groups inside a single column violate 1NF. Searching for a single suspect requires string parsing — no FK integrity possible.

✓ 1NF Compliant

After Decomposition

Incident(id, title)
IncidentSuspects(incident_id, person_id)

Every column now holds a single atomic value. The junction table enforces FK integrity and enables efficient WHERE person_id = ? lookups.

Applied in CMS: person_contacts, incident_suspects, case_officers all resolve multivalued attributes from earlier unnormalized designs.

Normalization · Step 2

Second Normal Form — Full Dependency

⚠ Partial Dependency

Unnormalized

OfficerTask(badge, task_id, officer_name, task_desc)

badge → officer_name  (partial!)
task_id → task_desc (partial!)

officer_name depends only on badge, not on the full composite key. If the officer's name changes, every task row must be updated — update anomaly.

✓ 2NF Compliant

After Decomposition

users(badge, name, rank, …)
tasks(task_id, description, …)
officer_tasks(badge, task_id, assigned_at)

Every non-key attribute now depends on the entire primary key. No update anomalies — officer name change requires a single row update in users.

Applied in CMS: case_officers(case_id, user_id, role) — role depends on the full composite key, not just either half.

Normalization · Step 3

Third Normal Form — Transitive Elimination

⚠ Transitive Dependency

Unnormalized

Location(area_id, area_name, city_name, province_name)

area_id → city_name
city_name → province_name  (transitive!)

province_name depends on city_name, which depends on area_id. Renaming a province requires touching every area row — massive redundancy.

✓ 3NF Compliant

After Decomposition

provinces(id, name)
districts(id, name, province_id)
cities(id, name, district_id)
areas(id, name, city_id, lat, lng)

The 5-level geo hierarchy (country → province → district → city → area) eliminates all transitive dependencies. A single UPDATE to provinces propagates everywhere.

Applied in CMS: Exact 5-table hierarchy implemented in schema. crime_types(id, name, category_id) follows the same pattern.

Constraints & Views

Integrity Constraints Deployed

PRIMARY KEY (all tables) FOREIGN KEY + referential actions UNIQUE (badge_number, national_id…) NOT NULL on critical columns CHECK (failed_login_attempts ≥ 0) DEFAULT (CURRENT_TIMESTAMP) ON UPDATE CASCADE ON DELETE RESTRICT / CASCADE / SET NULL

Composite Index Strategy

INDEX idx_area_geo (latitude, longitude)
INDEX idx_session_user (user_id)
INDEX idx_incident_status (status)
INDEX idx_case_opened_at (opened_at)

Indexes cover the columns most frequently used in WHERE and JOIN predicates, reducing full table scans on large tables.

Analytical View: v_active_cases

CREATE VIEW v_active_cases AS
 SELECT cf.case_number, ci.title,
   CONCAT(p.first_name,' ',p.last_name) investigator,
   DATEDIFF(NOW(), cf.opened_at) days_open
 FROM case_files cf
 JOIN crime_incidents ci ON ci.id = cf.incident_id
 JOIN users u ON u.id = cf.lead_investigator_id
 JOIN persons p ON p.id = u.person_id
 WHERE cf.status != 'CLOSED';

Why Views Matter Here

Views act as a security boundary — the UI layer queries v_active_cases without needing JOIN logic or direct table access. Different roles get different views, enforcing least-privilege data exposure.

Physical Schema · Business Logic

Integrity Triggers

Trigger 1 : Warrant Validation

CREATE TRIGGER trg_warrant_not_expired
BEFORE INSERT ON arrest_records
FOR EACH ROW BEGIN
 IF EXISTS (SELECT 1 FROM warrants
  WHERE id = NEW.warrant_id
  AND expires_at < CURDATE()) THEN
  SIGNAL SQLSTATE '45000'
  SET MESSAGE_TEXT='Expired warrant';
 END IF; END;

Trigger 2 : Audit Log (AFTER UPDATE)

CREATE TRIGGER trg_audit_evidence
AFTER UPDATE ON evidence
FOR EACH ROW
 INSERT INTO audit_logs
 (table_name, record_id, action, old_data, new_data, changed_by, changed_at)
 VALUES('evidence', OLD.id, 'UPDATE',
  JSON_OBJECT('status',OLD.status),
  JSON_OBJECT('status',NEW.status),
  @current_user_id, NOW());

Why Triggers vs. Application Code?

✓ Bypass-proof : enforced even if the application has a bug or is bypassed by direct DB access
✓ Warrant check fires on every INSERT to arrest_records : legally mandated
✓ Audit triggers capture old/new JSON values : court-admissible, immutable trail
✓ BEFORE triggers validate before the row is committed; AFTER triggers log after commit

Critical Reflection

Design Decisions & Lessons Learned

Issue · Resolved

Weak Password Storage

Initial prototype stored plaintext passwords. Resolved by applying BCrypt (cost factor 12) to password_hash. Schema enforces VARCHAR(255) minimum for hash storage.

Issue · Resolved

Schema : Code Drift

JPA entity classes fell out of sync with the physical schema after incremental changes. Solution: rebuilt schema_enhanced.sql from validated entity models; enforced forward-engineering discipline.

Design Choice

Surrogate vs. Natural Keys

We chose surrogate BIGINT AUTO_INCREMENT PKs everywhere. Natural keys (badge_number, national_id) are exposed as UNIQUE constraints : best of both worlds.

Trade-off

Denormalization for Audit Log

audit_logs stores JSON snapshots of old/new data : intentional denormalization for forensic read performance. A query on audit history must not require JOINs across 31 tables.
