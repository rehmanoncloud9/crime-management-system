Passwords stored as BCrypt hashes at cost factor 12. Session tracking in login_sessions. Brute-force lockout enforced via failed_login_attempts counter with a database CHECK constraint.

Conceptual Design

Entity Relationship Diagram

Conceptual to Relational

ER-to-Relational Mapping

Rule 1 · Strong Entities

Direct Table Mapping

Each strong entity becomes a relation. Surrogate BIGINT AUTO_INCREMENT PKs used throughout. Natural keys exposed as UNIQUE constraints.

Rule 2 · Weak Entities

Inherited PKs with CASCADE DELETE

evidence depends on case_files. FK declared ON DELETE CASCADE so orphan evidence records are structurally impossible.

Rule 3 · ISA Hierarchy

Table-per-Subtype Strategy

persons is the supertype. users and civilians share its PK via a 1:1 FK, keeping subtypes independent without attribute duplication.

Rule 4 · Binary M:N

Junction Tables with Attributes

The Case-Officer M:N becomes case_officers(case_id, officer_id, role, assigned_at). The junction carries descriptive attributes beyond just the two keys.

Rule 5 · Multivalued Attributes

Separate Lookup Tables

A person's multiple phone numbers map to person_contacts(person_id, type, value). This eliminates repeating groups and restores 1NF.

Rule 6 · Referential Actions

Semantically Correct Cascades

RESTRICT on court-critical parent records. CASCADE only where child rows are meaningless without parent. SET NULL for soft references like created_by.

Normalization · Step 1

First Normal Form: Atomicity

Violation

Unnormalized Incident Record

Incident(id, title, date, location, suspects)
suspects = "Ali, Ahmed, Sara"

A multi-value column inside one cell violates 1NF. Searching for a single suspect requires string parsing; no FK constraint is possible.

1NF Compliant

After Decomposition

Incident(id, title, date, location)
IncidentSuspects(incident_id, person_id)

Every column now holds exactly one atomic value. The junction table enforces FK integrity and enables an efficient WHERE person_id = ? index lookup.

Applied in CMS: person_contacts, incident_suspects, and case_officers all resolve multi-valued attributes from earlier unnormalized designs.

Normalization · Step 2

Second Normal Form: Full Dependency

Partial Dependency

Same Incident Record, Extended

IncidentOfficer(incident_id, badge, officer_name, assignment_date)

badge → officer_name  (partial!)
officer_name depends only on badge, not on the full composite key.

Changing an officer name requires updating every incident row that officer appears in. This is a classic update anomaly.

2NF Compliant

After Decomposition

users(badge, officer_name, rank, ...)
IncidentOfficer(incident_id, badge, assignment_date)

Every non-key attribute now depends on the entire primary key. A name change requires updating exactly one row in users.

Applied in CMS: case_officers(case_id, user_id, role, assigned_at). The role attribute depends on the full composite key, not either half alone.

Normalization · Step 3

Third Normal Form: Transitive Elimination

Transitive Dependency

Same Incident Record, Location Data

Incident(id, title, area_name, city_name, province_name)

id → city_name
city_name → province_name  (transitive!)

Renaming a province requires touching every incident row from that province. Pure redundancy and a deletion anomaly risk.

3NF Compliant

After Decomposition

provinces(id, name)
districts(id, name, province_id)
cities(id, name, district_id)
areas(id, name, city_id, lat, lng)
Incident(id, title, area_id)

The full 5-level geo hierarchy removes all transitive dependencies. A province rename is a single-row update in provinces.

Applied in CMS: Exactly this 5-table hierarchy is live in schema_enhanced.sql. The single Incident Record has now been traced cleanly from UNF to 3NF.

Integrity Constraints Deployed

Composite Index Strategy

INDEX idx_area_geo (latitude, longitude)
INDEX idx_session_user (user_id)
INDEX idx_incident_status (status)
INDEX idx_case_opened_at (opened_at)

Indexes cover columns most frequently used in WHERE and JOIN predicates, preventing full table scans on large operational tables.

View: v_active_cases

CREATE VIEW v_active_cases AS
 SELECT cf.case_number, ci.title,
   CONCAT(p.first_name, ' ', p.last_name) investigator,
   DATEDIFF(NOW(), cf.opened_at) days_open
 FROM case_files cf
 JOIN crime_incidents ci ON ci.id = cf.incident_id
 JOIN users u ON u.id = cf.lead_investigator_id
 JOIN persons p ON p.id = u.person_id
 WHERE cf.status != 'CLOSED';

Why Views Matter Here

Views act as a security boundary. The UI queries v_active_cases without needing JOIN logic or direct table access. Different roles get different views, enforcing least-privilege data exposure at the schema level.

Physical Schema · Business Logic

Integrity Triggers

Trigger 1 · Warrant Validation (BEFORE INSERT)

CREATE TRIGGER trg_warrant_not_expired
BEFORE INSERT ON arrest_records FOR EACH ROW
BEGIN
 IF EXISTS (SELECT 1 FROM warrants
  WHERE id = NEW.warrant_id AND expires_at < CURDATE())
 THEN SIGNAL SQLSTATE '45000'
  SET MESSAGE_TEXT = 'Warrant expired';
 END IF; END;

Trigger 2 · Audit Log (AFTER UPDATE)

CREATE TRIGGER trg_audit_evidence
AFTER UPDATE ON evidence FOR EACH ROW
 INSERT INTO audit_logs
 (table_name, record_id, action, old_data, new_data, changed_by)
 VALUES('evidence', OLD.id, 'UPDATE',
  JSON_OBJECT('status', OLD.status),
  JSON_OBJECT('status', NEW.status), @current_user_id);

BEFORE vs. AFTER: Why It Matters

BEFOREValidates before the row is committed. A SIGNAL rolls back the entire transaction. Used for legal constraint checks like expired warrants.
AFTERLogs after a successful commit. Guarantees the audit entry reflects what was actually persisted in the database.
Bypass-proofEnforced even if the application has a bug or a DBA runs direct SQL. The database itself is the last line of defence.

Physical Schema · Procedural

Stored Procedures

Encapsulating Business Logic

Stored procedures move critical "state change" logic into the database engine. This ensures that no matter which application connects, the business rules are applied identically.

Case Closure Procedure (`sp_close_case`)

This procedure handles the sensitive operation of closing a case. It validates prerequisites, updates the status, and mandates an audit log entry within a single atomic transaction.

Key Advantages

  • Atomicity Status update and Audit Log entry happen together or not at all.
  • Maintenance Rules can be updated in one place without re-deploying the Java app.
  • Abstraction Application only needs to call CALL sp_close_case(...).

Implementation Detail

CREATE PROCEDURE sp_close_case(
  IN p_case_id BIGINT, IN p_status VARCHAR(50),
  IN p_reason TEXT, IN p_user_id BIGINT
)
BEGIN
  START TRANSACTION;

  -- 1. Validate parameters (omitted for brevity)

  -- 2. Execute Primary Update
  UPDATE case_files SET status = p_status,
    closed_at = NOW(), closure_reason = p_reason
  WHERE id = p_case_id;

  -- 3. Forced Audit Entry (cannot be bypassed)
  INSERT INTO audit_logs(user_id, action, description)
  VALUES(p_user_id, 'CLOSE_CASE', 'Case closed...');

  COMMIT;
END$$

*Procedure logic ensures that "Closure" and "Audit" are tightly coupled at the engine level.

FK Validation

InnoDB rejects any INSERT where crime_type_id or area_id do not exist in their parent tables. This happens before the application ever sees a response.

Trigger Chain

A single INSERT on arrest_records fires the BEFORE warrant check, then on success fires the AFTER audit log. Two triggers, one transaction.

View Refresh

The dashboard re-queries v_active_cases after every commit. Because views are virtual, the UI always reflects the live state of the database.

Critical Reflection

Design Decisions and Trade-offs

Issue · Resolved

Weak Password Storage

Initial prototype stored plaintext passwords. Resolved by applying BCrypt at cost factor 12 to the password_hash column. Schema enforces VARCHAR(255) minimum to accommodate the full hash string.

Issue · Resolved

Dashboard Query Complexity

The investigator dashboard required JOINs across five tables, causing performance bottlenecks. Resolved by implementing the v_active_cases analytical view, which encapsulates the joining logic and optimizes retrieval speed at the schema level.

Design Choice

Surrogate vs. Natural Keys

Surrogate BIGINT AUTO_INCREMENT PKs used throughout for join performance and stability. Natural keys such as badge_number and national_id are exposed as UNIQUE constraints, giving both benefits simultaneously.

Intentional Trade-off

Denormalization in Audit Log

audit_logs stores JSON snapshots of old and new data. This is deliberate denormalization for forensic read performance. A historical query must not require JOINs across 31 tables to reconstruct a past state.
